# Создание плагинов для Toshy

Подробное руководство для разработчика, который впервые открыл исходники Toshy.

**Редакция:** 21 октября 2026 года. **Формат пакета:** `schema_version: 1`. **API плагинов:** `1`.

Руководство сверено с проектом `toshy-to-gpt-11`. Примеры относятся к существующей реализации, а не к планам развития. Если интерфейс вашей версии отличается, начните с проверки версии Toshy и состава установленного обновления плагинов.

Примеры прошли проверку синтаксиса Python и JSON, проверки манифестов и упаковки штатными средствами проекта. Пример счётчика дополнительно проверен с настоящими Qt-виджетами в режиме без экрана; проверены добавление второго компонента, сохранение данных, слот, обработчик события, таймер, простая замена и обёртка вызова инструмента. Это не заменяет проверку вашего готового плагина в полной рабочей конфигурации и на заявленных ОС.

## 1. Что такое плагин

Плагин — отдельный устанавливаемый пакет, который добавляет или изменяет возможности Toshy. Например, он может добавить инструмент агента, боковой виджет, новую рабочую вкладку или расширение существующей панели.

Один плагин может одновременно содержать несколько модулей, несколько виджетов, воркспейс, кнопки верхней панели и обработчики событий. Всё это распространяется одним ZIP-архивом и включается одним переключателем плагина.

Плагин хранит свой код внутри собственного пакета. Установка не должна заменять `run_ui.py`, переписывать исходники чата или копировать изменённые файлы поверх `ui/` и `core/`. Toshy читает описание пакета и подключает его части через механизм плагинов.

При этом плагин — настоящий Python-код с доступом, который имеет процесс Toshy. Это не изолированная песочница и не декларативная настройка внешнего вида. Проверка структуры ZIP не доказывает безопасность поведения кода.

### Как пакет превращается в работающую функциональность

1. Менеджер проверяет архив и читает `plugin.json`.
2. Пакет устанавливается в отдельную папку своего ID и версии.
3. Пользователь включает плагин.
4. После полного перезапуска приложения Toshy проверяет совместимость, зависимости и конфликты.
5. Для выбранных компонентов загружаются Python-функции или модули.
6. Интерфейсные компоненты создаются в процессе UI, компоненты агента — в процессе ядра.

**Установка, включение и запуск модуля — разные действия.** Для обычного виджета достаточно включения плагина и перезапуска приложения. Если плагин добавляет модуль агента, этот модуль также должен быть включён и доступен нужному проекту по обычным правилам Toshy.

## 2. Термины: название, ID, компонент и шаблон

| Термин | Что означает | Пример |
| --- | --- | --- |
| Название плагина | Имя для человека; отображается в списке | `Помощник по тексту` |
| ID плагина | Постоянная техническая идентичность пакета | `alex.text-helper` |
| Версия плагина | Версия кода и описания пакета | `1.0.0` |
| Компонент | Одна подключаемая часть плагина | Виджет, модуль, кнопка |
| ID компонента | Уникальное имя части внутри этого плагина | `text-widget` |
| Полный ID компонента | ID плагина и локальный ID через `/` | `alex.text-helper/text-widget` |
| Системное имя модуля | Имя модуля в реестре агента | `alex_text_tools` |
| Шаблон | Стартовая заготовка файлов и описания | `Виджет` |
| Тег | Метка для поиска и классификации | `widget`, `text-tools` |
| Точка входа | Python-функция, которую вызывает Toshy | `plugin:create` |
| Цель, `target` | Существующий компонент или точка расширения | `ui.topbar.right` |

### Название и ID — зачем нужны оба

Название можно написать по-русски и впоследствии изменить. Оно нужно пользователю.

ID нужен менеджеру: по нему устанавливается обновление, находятся данные плагина и описываются зависимости. Если изменить ID опубликованного плагина, Toshy будет воспринимать пакет как другой плагин. Старые данные и зависимости не переедут автоматически.

Для нового плагина используйте собственный префикс: `alex.counter`, `myteam.project-tools`. В ID допустимы строчные латинские буквы, цифры, точки и дефисы по правилам формата. Начинайте с буквы; не используйте пробелы, кириллицу и подчёркивания. Надёжный образец: `author.my-plugin`.

ID компонента задаётся отдельно: `main`, `counter`, `text_tools`, `status-button`. Он должен быть уникален внутри плагина. Держитесь простых строчных имён, начинающихся с буквы; разделяйте слова одним `_` или `-`.

Системное имя модуля — ещё одно имя. Оно является Python-идентификатором: например, `alex_text_tools`, без точек и дефисов. Имена модулей должны быть уникальны во всём Toshy, включая системные и кастомные модули. Имена инструментов также выбирайте с собственным префиксом.

### Компоненты — на примере

Плагин `alex.text-helper` может содержать:

- `tools` — системный модуль с обработкой текста;
- `text-widget` — виджет с кнопками для пользователя;
- `workspace` — отдельную рабочую вкладку;
- `toolbar` — кнопку на верхней панели.

Это четыре компонента одного пакета. Они не обязаны находиться в одном Python-файле. Но и каждый Python-файл не обязан становиться компонентом: `utils.py` с вспомогательными функциями — обычный внутренний файл.

### Шаблон — не тег и не ограничение

Выбор шаблона **создаёт файлы и начальное описание компонента**. Тег только помогает найти пакет в библиотеке.

Шаблон «Виджет» не запрещает добавить модуль или воркспейс в этот же плагин. «Без шаблона» создаёт пустую основу пакета; поведение нужно добавить самостоятельно или кнопкой «Добавить компонент…».

Заготовка не генерирует готовую бизнес-логику по описанию. Например, описание «калькулятор» не превратит стандартный виджет в калькулятор: это поведение нужно написать на Python.

## 3. Что понадобится разработчику

- Рабочая копия Toshy с поддержкой менеджера плагинов.
- Тот же Python и окружение, которыми запускается Toshy.
- Редактор кода и базовое знание Python.
- Для интерфейса — основы Qt: `QWidget`, компоновки, сигналы и слоты.
- Для инструментов — понимание `async def` и JSON Schema.

Не нужно предварительно изучать весь исходный код агента. Для первого независимого виджета достаточно примера ниже. Для модификации встроенного чата потребуется дополнительно изучить его интерфейс и доступные точки расширения.

Создайте отдельную папку исходников, например `ToshyPluginSources`. Храните её отдельно от установленных версий в `plugins/packages/`. Для экспериментов удобно иметь отдельную копию Toshy без важных рабочих данных.

Git полезен для истории изменений, но не обязателен для локального создания и импорта ZIP. Авторизация GitHub не нужна, чтобы установить локальный пакет или скачать готовый пакет из публичного релиза.

## 4. Как устроен менеджер плагинов

Откройте контекстное меню верхней панели Toshy и выберите «Плагины». В менеджере три вкладки: «Установленные», «Библиотека», «Экспорт».

### 4.1. Установленные

Здесь находятся установленные пакеты. У карточки есть название, описание, изображение, теги, версия и переключатель включения.

Порядок меняется перетаскиванием за ручку карточки. Выше — больший приоритет. Жёлтый предупреждающий значок показывает причины конфликтов или несовместимости при наведении.

Переключатель сохраняет выбор для следующего запуска. Сообщение «Изменения применятся после перезапуска приложения» означает именно полный выход из Toshy и повторный запуск. Остановка и запуск одного ядра этого не заменяют.

Контекстное меню установленного пакета позволяет выбрать его для экспорта или удалить. Экспорт установленного пакета — способ получить его текущий состав, а не автоматическое создание редактируемого проекта. Для разработки держите собственные исходники отдельно.

### 4.2. Библиотека

Здесь находятся:

| Элемент | Назначение |
| --- | --- |
| Репозиторий каталога плагинов | Адрес общего каталога; это не ссылка на исходники вашего текущего плагина |
| Сохранить | Сохранить адрес каталога |
| Обновить список | Загрузить список пакетов из выбранного каталога |
| Импорт ZIP… | Установить готовый локальный пакет |
| Импорт с GitHub… | Скачать готовый пакет из публичного GitHub Release |
| Поиск и теги | Отфильтровать список каталога |
| Установить / Обновить | Установить выбранную версию по явному действию пользователя |

В этой редакции официальный адрес по умолчанию может быть пустым. Это не мешает локальному импорту или прямому импорту с GitHub.

### 4.3. Экспорт: что означает каждое поле

| Элемент | Что вводить или выбирать |
| --- | --- |
| Исходники плагина | Папку, непосредственно внутри которой находится `plugin.json` |
| Папка… | Выбрать существующую папку исходников |
| Шаблон | Тип создаваемой заготовки или следующего добавляемого компонента |
| ID | Постоянный ID **всего нового плагина**, например `alex.counter` |
| Название | Читаемое название нового плагина |
| Автор | Имя, псевдоним или название команды |
| Описание | Краткое объяснение функций пакета |
| Картинка / PNG… | PNG для новой заготовки; при пустом поле создаётся стандартная картинка |
| Компоненты | Список частей выбранного пакета и их количество |
| Добавить компонент… | Создать дополнительную часть в выбранной папке исходников |
| Создать исходники… | Создать **новую папку плагина**, а не установить или запустить его |
| Проверить состав | Проверить описание и файлы; показать, что попадёт в ZIP |
| Экспорт ZIP… | Упаковать проверенные исходники в устанавливаемый архив |

**Важная особенность текущего интерфейса:** поля ID, названия, автора, описания и картинки используются кнопкой «Создать исходники…». Они не являются редактором метаданных уже выбранного плагина. Для существующего пакета меняйте `plugin.json` и соответствующие файлы в папке исходников.

Выбор пункта в списке «Компоненты» также не открывает редактор Python-кода и не меняет его. Это обзор состава пакета. Встроенного удаления компонентов или редактора режимов `extend` / `replace` здесь пока нет: такие изменения вносятся в файлы вручную.

Кнопка «Создать исходники…» сначала спрашивает родительскую папку. Внутри неё создаётся подпапка с ID плагина. Например, при выборе `ToshyPluginSources` и ID `alex.counter` результатом будет `ToshyPluginSources/alex.counter/`.

Поле «Исходники плагина» не задаёт место создания этой новой папки: для создания используется отдельный диалог. После успешного создания поле переключится на получившуюся папку автоматически.

## 5. Первый плагин: виджет со счётчиком

Этот пример добавляет независимый боковой виджет. Он не требует ядра, модели или сторонних Python-зависимостей сверх окружения Toshy.

### Шаг 1. Создайте заготовку

В «Плагины → Экспорт» укажите:

| Поле | Значение |
| --- | --- |
| Шаблон | Виджет |
| ID | `author.counter` — замените `author` своим префиксом перед публикацией |
| Название | Счётчик |
| Автор | Ваше имя |
| Описание | Простой виджет со счётчиком нажатий |
| Картинка | Можно оставить пустой |

Нажмите «Создать исходники…» и выберите родительскую папку. Не выбирайте в качестве результата уже существующий проект с тем же ID: генератор не перезаписывает существующую папку.

Внутри новой папки появятся `plugin.json`, `plugin.py`, `README.md`, `LICENSE`, `icon.png`. Сохраните все эти файлы.

### Шаг 2. Напишите код

Откройте созданный `plugin.py` в редакторе и замените содержимое:

```python
from PySide6.QtWidgets import QWidget, QVBoxLayout, QLabel, QPushButton


class CounterWidget(QWidget):
    def __init__(self, parent=None):
        super().__init__(parent)
        self.count = 0

        layout = QVBoxLayout(self)
        self.label = QLabel("Нажатий: 0", self)
        button = QPushButton("Добавить 1", self)
        button.clicked.connect(self.increment)

        layout.addWidget(self.label)
        layout.addWidget(button)
        layout.addStretch()

    def increment(self):
        self.count += 1
        self.label.setText(f"Нажатий: {self.count}")


def create(context):
    return CounterWidget(context.parent)
```

`create` — точка входа. Toshy вызовет её с контекстом, получит `QWidget` и поместит его в собственную боковую панель с заголовком и управлением перемещением. Для **добавления** виджета не нужно самостоятельно создавать ещё один `DockPanel`.

Не создавайте `QApplication` и не вызывайте `app.exec()` в коде плагина: приложение уже запущено. Этот файл также не предназначен для запуска командой `python plugin.py` как отдельная программа.

Счётчик в этом примере хранится только в памяти: после перезапуска снова будет ноль. Сохранение данных рассмотрено отдельно ниже.

### Шаг 3. Проверьте описание

Проверьте созданный `plugin.json`. Ниже полный допустимый вариант для этого примера; `LICENSE` и `icon.png` уже созданы генератором.

```json
{
  "schema_version": 1,
  "id": "author.counter",
  "version": "1.0.0",
  "name": "Счётчик",
  "description": "Простой виджет со счётчиком нажатий",
  "author": "Ваше имя",
  "license": "MIT",
  "image": "icon.png",
  "tags": ["productivity"],
  "compatibility": {
    "api": 1,
    "python": ">=3.12",
    "platforms": ["linux", "windows"]
  },
  "files": ["LICENSE", "README.md", "icon.png", "plugin.py"],
  "components": [
    {
      "id": "main",
      "type": "widget",
      "mode": "add",
      "title": "Счётчик",
      "entrypoint": "plugin:create",
      "placement": "right_top"
    }
  ]
}
```

### Шаг 4. Экспортируйте

1. Убедитесь, что «Исходники плагина» указывает на папку с этим `plugin.json`.
2. Нажмите «Проверить состав».
3. Проверьте список включаемых файлов.
4. Нажмите «Экспорт ZIP…».
5. Сохраните архив **за пределами папки исходников**.

Экспорт не устанавливает плагин и не запускает его код. Это подготовка пакета для установки.

### Шаг 5. Установите и включите

1. Откройте вкладку «Библиотека».
2. Нажмите «Импорт ZIP…» и выберите полученный архив.
3. Прочитайте подтверждение установки стороннего кода.
4. Перейдите в «Установленные» и включите «Счётчик».
5. Полностью закройте Toshy и запустите снова.

Виджет должен появиться справа сверху. Нажатие кнопки увеличивает значение. Если он не появился, проверьте переключатель, предупреждения и журнал; остановка одного ядра вместо перезапуска приложения недостаточна.

### Шаг 6. Измените установленный пример правильно

Редактируйте исходный `plugin.py`, а не копию в `plugins/packages/`. После изменения уже установленного пакета увеличьте `version`, например до `1.0.1`, снова проверьте состав, экспортируйте, импортируйте и перезапустите Toshy.

Повторная установка другой сборки с теми же ID и версией запрещена: версия должна обозначать определённые байты пакета. Удаление и повторная установка нужны не для обычного выпуска обновлений; используйте повышение версии.

## 6. Как читать и редактировать plugin.json

`plugin.json` — манифест: описание того, **что подключать**, где лежит код и с чем пакет совместим. Он должен находиться в корне исходников и в корне экспортированного ZIP.

Это обычный JSON в UTF-8: двойные кавычки, без комментариев и завершающих запятых. Не добавляйте произвольные поля: неизвестные ключи отклоняются валидатором.

### 6.1. Поля всего пакета

| Поле | Значение |
| --- | --- |
| `schema_version` | Версия структуры манифеста; сейчас `1` |
| `id` | Стабильный ID плагина |
| `version` | Финальная числовая версия, например `1.0.0`, `1.0.1`, `2.0.0` |
| `name` | Название для пользователя |
| `description` | Описание функций |
| `author` | Автор или команда |
| `license` | Обозначение лицензии; файл `LICENSE` тоже обязателен |
| `image` | Относительный путь к PNG, JPEG или WebP |
| `tags` | Дополнительные английские теги; пустой список разрешён |
| `compatibility` | Требования к API, Python и платформе |
| `files` | Явный список файлов или папок, включаемых в пакет |
| `components` | Список компонентов; для установки и экспорта нужен хотя бы один |
| `homepage` | Необязательная домашняя страница |
| `requires_packages` | Необязательные Python-зависимости всего пакета |
| `requires_plugins` | Необязательные зависимости от других плагинов |

Первые обязательные поля видны в полном примере выше. `homepage` и поля зависимостей можно не указывать.

Не используйте суффиксы версий вроде `1.0.0-dev`, `1.0.0+local`, `1.0.0.post1`: текущая установка рассчитана на финальные числовые версии. Префикс `v` не является частью значения `version`.

Теги типов (`widget`, `workspace`, `top-bar`, `core`, `system-module`, `custom-module`) менеджер может добавлять при отображении по составу компонентов. Дополнительные теги задавайте строчными английскими словами с дефисами: `text-tools`, `productivity`, `pipeline-nodes`.

### 6.2. Совместимость

```json
{
  "api": 1,
  "python": ">=3.12",
  "platforms": ["linux", "windows"]
}
```

Это **значение поля `compatibility`**, а не отдельный полный манифест. Укажите реальные требования своего кода. Если используете синтаксис Python 3.14, нельзя оставлять `>=3.12` только потому, что так сделал шаблон.

Необязательное ограничение `toshy` поддерживается форматом, но имеет смысл только когда сборка хоста передаёт свою версию для проверки. Не заполняйте его случайным номером: неизвестная версия хоста тоже может привести к блокировке.

### 6.3. Поля компонента

| Поле | Назначение |
| --- | --- |
| `id` | Локальный ID компонента |
| `type` | `widget`, `workspace`, `topbar`, `core`, `system-module` или `custom-module` |
| `mode` | `add`, `extend` или `replace` |
| `entrypoint` | Python-модуль и функция: `plugin:create` |
| `path` | Папка содержимого модуля; используется вместо `entrypoint` |
| `title` | Читаемый заголовок этой части; иначе обычно берётся название плагина |
| `placement` | Начальное размещение интерфейсного компонента |
| `module_name` | Системное имя компонента-модуля |
| `target` | Цель расширения или замены |
| `operation` | Способ подключения к точке расширения |
| `requires_packages` | Python-зависимости только этого компонента |
| `requires_components` | Зависимости от конкретных компонентов |
| `requires_contracts` | Нужные интерфейсы и диапазоны их версий |
| `provides_contracts` | Сохранённые/предоставляемые интерфейсы и их версии |
| `group` | Связанная группа компонентов внутри плагина |
| `extension_points` | Собственные точки расширения плагина |

У компонента должна быть **ровно одна** из двух форм загрузки: `entrypoint` или `path`. `path` разрешён только системным и кастомным модулям.

Пример `plugin:create` означает: найти `plugin.py` в пакете и вызвать его функцию `create(context)`. Для `components.status.plugin:create` путь к коду — `components/status/plugin.py`.

Все пути внутри манифеста относительные, с `/`, даже на Windows. `C:\\...`, `/home/...` и переходы `../` не подходят для путей содержимого пакета.

### 6.4. Размещение

| Тип | Практически используемые значения `placement` |
| --- | --- |
| `widget`, режим `add` | `left_top`, `left_bottom`, `right_top`, `right_bottom` |
| `workspace`, режим `add` | `top`, `bottom` |
| `topbar`, режим `add` | `left`, `right` |

Виджет может быть впоследствии перемещён пользователем; сохранённое положение имеет приоритет над начальным. Для `extend` с `operation: "slot"` место определяет `target`, а не `placement`.

## 7. Несколько компонентов в одном плагине

### Через интерфейс

1. Выберите существующую **папку исходников** в верхней строке экспорта.
2. В «Шаблон» выберите тип следующего компонента.
3. Нажмите «Добавить компонент…».
4. Укажите новый локальный ID компонента.
5. Для системного или кастомного модуля выберите папку готового модуля и его уникальное системное имя.
6. Проверьте новый список компонентов и состав файлов.

ID, название и автор всего плагина сохраняются. Добавление компонента не создаёт отдельный установленный плагин.

Новые исходники размещаются в `components/<имя_компонента>/`. Дефисы имени папки заменяются подчёркиваниями, поэтому избегайте пары ID вроде `text-tools` и `text_tools`: они претендуют на одну папку.

«Без шаблона» в этом диалоге не добавляется как компонент. Чтобы добавить часть, выберите содержательный тип.

Список компонентов в интерфейсе — обзор. Для редактирования уже добавленной части откройте её файлы. Чтобы убрать её вручную, согласованно измените `components`, `files`, связанные зависимости и сами файлы. Работайте с исходной копией под контролем версий.

### Пример: добавьте индикатор к счётчику

Выберите исходники `author.counter`, шаблон «Верхняя панель» и добавьте компонент с ID `status`. Откройте `components/status/plugin.py`:

```python
from PySide6.QtWidgets import QLabel


def create(context):
    label = QLabel("Счётчик подключён", context.parent)
    label.setToolTip("Плагин author.counter активен")
    return label
```

У добавленного компонента можно указать `placement: "right"`. Теперь пакет содержит виджет и элемент верхней панели. По умолчанию генератор не связывает их состояние: чтобы индикатор показывал число нажатий, вам потребуется написать обмен данными между этими двумя UI-компонентами.

У каждого добавленного модуля может быть собственная папка и собственный `module_name`. Так можно упаковать несколько кастомных модулей и виджет в один ZIP.

Автоматическое добавление не повышает версию пакета за вас. Если предыдущая версия уже устанавливалась, увеличьте `version` перед следующим экспортом.

## 8. Что создаёт каждый шаблон

| Шаблон в интерфейсе | Что получается | Что нужно сделать автору |
| --- | --- | --- |
| Без шаблона | Метаданные, картинка, лицензия, README, пустой `components` | Добавить хотя бы один компонент и его код |
| Кастомный модуль | Упакованная копия выбранного готового модуля | Подготовить модуль с `__init__.py`; проверить переносимые настройки |
| Системный модуль | Упакованная копия выбранного готового модуля | Подготовить модуль; задать уникальное системное имя |
| Виджет | `QLabel` как простейший `QWidget`, добавляемый в боковую панель | Заменить содержимое своим интерфейсом |
| Воркспейс | `QLabel` как содержимое новой рабочей вкладки | Создать нужный `QWidget`; при необходимости поменять размещение |
| Верхняя панель | Простой `QWidget` для добавления на верхнюю панель | Реализовать кнопку, индикатор или другую компактную область |
| Ядро | Функция `create(context)`, пока возвращающая `None` | Написать регистрацию/объект либо вручную описать нужное расширение |
| Узлы пайплайна | Системный модуль с двумя примерами операций и схемами аргументов | Адаптировать операции, названия, схемы и реализацию |

### «Без шаблона»

Это полноценная исходная папка, но ещё не устанавливаемый плагин. Пока `components` пуст, «Проверить состав», экспорт и установка должны отказать с просьбой добавить компонент. Пустая заготовка удобна для сложного пакета, который вы хотите собрать самостоятельно.

### Модули

Текущий интерфейс шаблонов модулей **упаковывает уже подготовленный модуль**, а не открывает мастер написания инструмента. Диалог попросит выбрать его папку. Минимальный пример подготовки приведён в следующей главе.

При создании нового пакета имя исходной папки используется как системное имя модуля. Поэтому заранее назовите её корректным Python-идентификатором, например `alex_text_tools`. При добавлении модуля к существующему плагину интерфейс отдельно запрашивает это имя.

Шаблоны UI не становятся автоматически интерфейсами модуля. Если виджет должен управлять модулем ядра, связь через мост приложения нужно реализовать отдельно; наличие обоих компонентов в ZIP лишь устанавливает их вместе.

### «Узлы пайплайна»

Это отдельный удобный шаблон, но не седьмой тип компонента в формате `plugin.json`. Он создаёт `type: "system-module"` и дополнительный тег `pipeline-nodes`. Операции этого модуля редактор обнаруживает как ноды.

## 9. Модуль с инструментом для агента

Модуль отвечает за функциональность агента. Виджет отвечает за интерфейс пользователя. Для нового инструмента не обязательно создавать виджет.

### 9.1. Подготовьте исходную папку модуля

Создайте отдельную папку `author_text_tools` и файл `__init__.py` внутри неё:

```python
from core.registry import BaseModule, BaseTool


class UppercaseTool(BaseTool):
    pipeline_title = "Текст в верхнем регистре"

    def __init__(self):
        super().__init__(
            name="author_text_uppercase",
            description="Перевести переданный текст в верхний регистр.",
            args_schema={
                "type": "object",
                "properties": {
                    "text": {"type": "string", "description": "Исходный текст"}
                },
                "required": ["text"],
                "additionalProperties": False,
            },
        )

    async def execute(self, text):
        return text.upper()


class Module(BaseModule):
    def get_tools(self):
        return [UppercaseTool()]
```

Имя `Module` важно: так Toshy получает экземпляр содержимого модуля. `get_tools()` возвращает инструменты. `name` инструмента — стабильное техническое имя, `description` объясняет его назначение модели, `args_schema` описывает входы, `execute` выполняет действие.

`args_schema` — JSON Schema. `string`, `integer`, `number`, `boolean`, `array`, `object` задают типы; `required` перечисляет обязательные поля. Аргументы схемы должны совпадать с параметрами `execute`.

Для удобного названия модуля в редакторе можно создать `ui/config.json` внутри исходной папки модуля:

```json
{
  "display_name": "Инструменты текста",
  "color": "#34b4a1"
}
```

### 9.2. Упакуйте модуль

В экспорте выберите «Кастомный модуль» или «Системный модуль», заполните данные нового плагина, нажмите «Создать исходники…» и укажите подготовленную папку `author_text_tools`, когда диалог её запросит.

Генератор копирует модуль в пакет. Получится компонент примерно такого вида:

```json
{
  "id": "main",
  "type": "custom-module",
  "mode": "add",
  "module_name": "author_text_tools",
  "path": "module"
}
```

Это **элемент массива `components`**. В `files` должна быть включена папка `module`. У системного варианта меняется `type` на `system-module`.

После копирования редактируйте модуль **в папке исходников плагина**. Изменения в первоначальной внешней папке автоматически в копию не попадают.

### 9.3. Сделайте инструмент доступным

Экспортируйте и установите пакет, включите плагин, полностью перезапустите Toshy. Затем включите добавленный модуль в конфигурации ядра и разрешите его нужной папке проекта по правилам приложения. Выберите подходящую сессию и запустите ядро.

Только после этого проверяйте, может ли модель вызвать `author_text_uppercase`. Плагин может быть установлен корректно, но его инструмент не будет доступен в проекте, которому модуль не разрешён.

### 9.4. Дополнительный жизненный цикл модуля

У `BaseModule` есть методы для инициализации и освобождения ресурсов, включая `async_init`, `deactivate`, `shutdown`, а также уведомления об изменении набора модулей. Для примера без внешних ресурсов они не нужны.

Если модуль открывает соединение или запускает процесс, используйте эти методы осмысленно: отключение модуля и завершение ядра должны освобождать ресурсы. Не поднимайте тяжёлые службы просто при импорте `__init__.py`.

## 10. Узлы пайплайна

Чтобы создать набор исполняемых нод, выберите «Узлы пайплайна». В заготовке есть два примера: перевод текста в верхний регистр и сложение чисел.

Их код находится в `module/__init__.py` или соответствующей папке вложенного компонента. Системное имя и имена операций генерируются с уникальным префиксом. Не переименовывайте их без необходимости после публикации: сохранённые графы ссылаются на технические идентификаторы.

### Как операция становится нодой

- Класс наследуется от `BaseTool`.
- В `super().__init__` указаны `name`, `description`, `args_schema`.
- `Module.get_tools()` возвращает экземпляр класса.
- По `args_schema.properties` редактор создаёт Arg-входы с типами.
- У ноды есть Exec-вход и Exec-выход, Prompt-вход и выход результата `result`.
- `pipeline_title` задаёт читаемое название карточки.

Prompt-вход относится к штатному механизму исполнения ноды; его не нужно добавлять как аргумент `execute(prompt=...)`, если операция не объявляет такой аргумент сама. Для определённой операции с заполненными входами вычисление может проходить напрямую, без запроса к модели.

Свойство `model_visible = False` в примерах означает: не предлагать операцию модели как обычный инструмент. Оно не запрещает прямое выполнение ноды. Если хотите и ноду, и инструмент модели, удалите этот флаг или установите `True`.

### Обнаружение при выключенном ядре

Редактор читает метаданные из `__init__.py` через AST, не выполняя код модуля. Поэтому пишите `name` и `args_schema` **непосредственно литералами** в вызове конструктора, как в примере предыдущей главы.

Вариант `name=build_name()` или `args_schema=SCHEMA` может работать в Python во время исполнения, но текущий статический анализатор не вычисляет эти выражения. Аналогично, классы только в других файлах не обнаруживаются этим простым проходом по `__init__.py` автоматически. При сложной реализации оставьте в `__init__.py` классы-адаптеры с буквальными метаданными, а тяжёлую логику вынесите в соседние файлы.

Статическое обнаружение не проверяет весь исполняемый код и не доказывает работоспособность ноды. После полного перезапуска приложение может показать ноды без ядра; для их запуска сам модуль должен быть включён и разрешён проекту.

В библиотеке редактора ищите `System modules → <название модуля>`. Проверяйте отдельную операцию, а не только карточку всего модуля: карточка модуля представляет иной уровень выполнения.

Текущий шаблон использует штатный выход `result`. Он не создаёт произвольный набор именованных выходных портов. Если вернуть словарь, это само по себе не превратит его ключи в новые выходы ноды.

## 11. API контекста и жизненный цикл

### 11.1. Функция-фабрика

Для компонента с `entrypoint` Toshy вызывает указанную функцию:

```python
def create(context):
    # Создайте объект или обработчик нужного типа.
    return None
```

Этот фрагмент показывает только сигнатуру. Возвращать `None` допустимо, например, для компонента `core/add`, выполняющего регистрацию. Для UI-добавления нужен `QWidget`, для расширения события — вызываемый обработчик. Неправильный тип результата блокирует компонент.

Фабрика должна быть синхронной. Не превращайте `create` в `async def`. Асинхронными могут быть обработчики соответствующих событий/операций ядра и методы модуля, но не создание Qt-виджета.

### 11.2. Что находится в context

| Свойство/метод | Что даёт |
| --- | --- |
| `context.plugin_id` | ID всего плагина |
| `context.component_id` | Полный ключ компонента, например `author.counter/main` |
| `context.plugin_dir` | `Path` папки выбранной установленной версии пакета |
| `context.data_dir` | `Path` отдельной папки пользовательских данных плагина; создаётся при обращении |
| `context.host` | Объект хоста для данного подключения |
| `context.app` | Псевдоним `host`; это не автоматически `QApplication` |
| `context.parent` | Родитель Qt-элемента при UI-создании; может отсутствовать в ядре |
| `context.default_factory` | Создание исходного компонента при поддерживаемой замене |
| `context.data` | Дополнительные данные конкретного подключения; тип зависит от точки |
| `context.runtime` | Механизм плагинов текущего процесса |
| `context.register_cleanup(callback)` | Зарегистрировать освобождение ресурсов компонента |

Контекст зависит от места вызова. При добавлении UI `host` обычно главное окно; в фабриках ядра и обработчиках подготовки — реестр модулей. Нельзя считать, что `context.host` всегда содержит `central_stack` или интерфейс чата.

При расширении `ui.chat.message.actions` поле `data` содержит словарь с `turn` и `kind`. При `ui.chat.input.actions` оно содержит объект текущего представления чата. При создании слотов верхней панели дополнительных данных может не быть. Учитывайте это, прежде чем обращаться к атрибутам.

### 11.3. Когда загружается код

- При проверке состава и распаковке ZIP код плагина не выполняется.
- После перезапуска подготовка загружает фабрики обработчиков событий и операций.
- Фабрики UI-слотов вызываются, когда хост заполняет соответствующую область. Например, кнопка сообщения создаётся для конкретного сообщения; фабрика может вызываться много раз.
- Независимые UI-добавления создаются при сборке интерфейса.
- `core/add` подготавливается в процессе ядра.
- Модули подключаются через реестр модулей и свой жизненный цикл.

Не начинайте действия с внешними последствиями на верхнем уровне импортируемого файла. Импорт может понадобиться при подготовке компонента ещё до пользовательского действия.

UI и ядро не разделяют общую Python-память. Глобальная переменная, изменённая виджетом, не является способом передать команду модулю ядра. Для связи изучайте существующий мост `ui/core_bridge/` и используйте соответствующие операции приложения. Универсального RPC-метода только из факта наличия `PluginContext` не появляется.

### 11.4. Очистка

Подписки, таймеры, открытые файлы, фоновые задания и процессы должны корректно завершаться. Для ресурсов фабрики используйте `context.register_cleanup`.

Пример **замены тела фабрики** интерфейсного компонента: индикатор, обновляемый таймером.

```python
from PySide6.QtCore import QTimer, QTime
from PySide6.QtWidgets import QLabel


def create(context):
    label = QLabel(context.parent)
    timer = QTimer(label)

    def update_clock():
        label.setText(QTime.currentTime().toString("HH:mm"))

    timer.timeout.connect(update_clock)
    timer.start(1000)
    update_clock()
    context.register_cleanup(timer.stop)
    return label
```

Включайте его в `widget/add`, `topbar/add` или подходящий UI-slot. Таймер привязан к `label` как родителю. Очистки вызываются в обратном порядке регистрации; не рассчитывайте на изменение порядка включением/выключением плитки во время текущей сессии приложения.

Если `core/add` возвращает объект с методом `close()`, runtime регистрирует его закрытие автоматически. Не регистрируйте тот же `close` второй раз без необходимости. Для сетевых/асинхронных ресурсов учитывайте доступность цикла событий и жизненный цикл ядра.

### 11.5. Потоки

Qt-виджеты создавайте и изменяйте в GUI-потоке. Тяжёлые вычисления, сетевые ожидания и большие чтения файлов не должны блокировать интерфейс. Результаты фоновых задач возвращайте через безопасный механизм сигналов/моста.

`async def` сам по себе не переносит вычисление на другое ядро процессора. Не запускайте бесконечный синхронный расчёт внутри асинхронного обработчика ядра. Для тяжёлого изолированного вычисления может быть уместен отдельный процесс, но это уже ответственность реализации плагина.

## 12. Расширение существующей функциональности

Есть три разных действия:

| Режим | Значение | Пример |
| --- | --- | --- |
| `add` | Добавить самостоятельный компонент | Новый виджет |
| `extend` | Подключиться к объявленной точке расширения | Дополнительная кнопка чата |
| `replace` | Выбрать альтернативную реализацию существующего компонента | Свой вариант встроенной панели |

В текущем интерфейсе базовые шаблоны создают `add`. Для `extend` и `replace` отредактируйте компонент в `plugin.json` и напишите подходящую фабрику. Выбор шаблона «Ядро» сам по себе не означает перехват всех действий агента.

### 12.1. Доступные встроенные точки расширения

| `target` | Вид | `operation` | Данные |
| --- | --- | --- | --- |
| `ui.topbar.left` | UI-slot | `slot` | Дополнительных данных может не быть |
| `ui.topbar.right` | UI-slot | `slot` | Дополнительных данных может не быть |
| `ui.chat.input.actions` | UI-slot | `slot` | Объект представления чата в `context.data` |
| `ui.chat.message.actions` | UI-slot | `slot` | `context.data`: `turn`, `kind` |
| `ui.ready` | Событие UI | `listen` | `payload`: `window` |
| `ui.workspace.changed` | Событие UI | `listen` | `payload`: `index`, `widget`; при смене верхнего рабочего представления |
| `core.ready` | Событие ядра | `listen` | `payload`: `registry` |
| `core.run_events` | События выполнения | `listen` | `payload`: `event`, `context`; потоковые `content` и `thought` здесь исключены |
| `core.tool.execute` | Операция ядра | `before`, `around`, `filter`, `after` | `payload`: `name`, `args`, `context` |

Это конкретные договорённости текущей реализации. Наличие похожего объекта в приложении не создаёт автоматически новый `target`. Например, нельзя произвольно написать `ui.file_manager.after_button`, если такая точка не объявлена и не вызывается хостом.

### 12.2. Пример: кнопка в верхней панели

Следующий JSON — **компонент для массива `components`**, а не полный файл:

```json
{
  "id": "hello-button",
  "type": "topbar",
  "mode": "extend",
  "target": "ui.topbar.right",
  "operation": "slot",
  "entrypoint": "hello:create"
}
```

Создайте `hello.py` в корне исходников и включите его в `files`:

```python
from PySide6.QtWidgets import QPushButton, QMessageBox


def create(context):
    button = QPushButton("Привет", context.parent)

    def show_message():
        QMessageBox.information(button, "Мой плагин", "Плагин подключён")

    button.clicked.connect(show_message)
    return button
```

Slot-фабрика возвращает сам `QWidget`, а не функцию-обработчик. Несколько независимых кнопок могут добавляться в одну область.

Событие `ui.ready` подходит для действий после создания основного интерфейса, но не превращает произвольный доступ к внутренним объектам в стабильный API. Если вручную переставляете кнопки по приватным атрибутам окна, такая интеграция требует повторной проверки после обновлений Toshy.

### 12.3. Пример: наблюдение за сменой воркспейса

Элемент `components`:

```json
{
  "id": "workspace-observer",
  "type": "workspace",
  "mode": "extend",
  "target": "ui.workspace.changed",
  "operation": "listen",
  "entrypoint": "observer:create"
}
```

Файл `observer.py`, который тоже нужно добавить в `files`:

```python
import logging


def create(context):
    logger = logging.getLogger("author.plugin.workspace")

    def on_workspace_changed(payload):
        logger.info("Верхний воркспейс переключён: %s", payload["index"])

    return on_workspace_changed
```

Здесь фабрика возвращает обработчик. Подписку на объявленное событие делает менеджер. Стандартный Python-логгер в примере использует конфигурацию хоста; не открывайте отдельный глобальный файл журнала при каждом событии.

Обработчики UI должны быть синхронными. Обработчик не должен менять основное системное сообщение агента или затрагивать несвязанные с его функцией данные.

### 12.4. Операционные хуки ядра

Операция отличается от события: у неё есть исполняемое действие и результат. Для `core.tool.execute` доступны:

| Операция | Сигнатура обработчика | Роль |
| --- | --- | --- |
| `before` | `handler(payload)` | Выполнить действие до цепочки; возвращаемое значение не заменяет запрос |
| `around` | `handler(next_call, payload)` | Обернуть дальнейшее выполнение; вернуть его итог |
| `filter` | `handler(result, payload)` | Вернуть преобразованный результат |
| `after` | `handler(result, payload)` | Наблюдать успешный итог; возвращаемое значение игнорируется |

В ядре обработчики могут быть асинхронными. Фабрика, возвращающая их, остаётся синхронной.

Пример компонента измерения длительности:

```json
{
  "id": "tool-timing",
  "type": "core",
  "mode": "extend",
  "target": "core.tool.execute",
  "operation": "around",
  "entrypoint": "timing:create"
}
```

Файл `timing.py`, включённый в `files`:

```python
from time import perf_counter


def create(context):
    from core.logger import core_logger

    async def measure(next_call, payload):
        started = perf_counter()
        try:
            return await next_call(payload)
        finally:
            elapsed = perf_counter() - started
            core_logger.event(
                "app",
                "PLUGIN_EVENT",
                f"{context.plugin_id}: {payload['name']} — {elapsed:.3f} с",
                level="INFO",
            )

    return measure
```

`next_call` — продолжение цепочки. Его разрешено вызвать **не более одного раза**. Если после выполнения инструмента возникла ошибка, нельзя автоматически повторять действие: оно могло уже изменить файл, отправить запрос или создать объект.

`before`/`after` находятся под управлением менеджера вне цепочки `around`. Фильтры применяются так, что более приоритетный получает последнее преобразование. Успешный результат инструмента не должен превращаться в ошибку только из-за сбоя наблюдателя `after`.

Не подменяйте в `payload` инструмент на недоступный текущему запуску. Штатный вызов использует разрешённый набор инструментов. Полные аргументы и контекст могут содержать чувствительные данные — не пишите их без необходимости в журнал.

### 12.5. Собственные точки расширения

Сложный плагин может объявить точку, к которой подключатся другие плагины. Имя должно находиться в его пространстве:

- `ui.plugin.<ID_плагина>.<имя>`;
- `core.plugin.<ID_плагина>.<имя>`.

Например, фрагмент **существующего компонента** плагина `author.counter`:

```json
{
  "extension_points": {
    "ui.plugin.author.counter.changed": {
      "strategy": "event",
      "version": "1.0"
    }
  }
}
```

Остальные обязательные поля компонента сохраняются. При изменении значения ваш UI-код может вызвать:

```python
context.runtime.emit(
    "ui.plugin.author.counter.changed",
    {"value": 10},
)
```

Это фрагмент внутри кода, где доступен `context`; он не является отдельным скриптом. Объявление в манифесте не генерирует вызов события — вы пишете его сами. Для операций и слотов также требуется реальное подключение в коде. Эти события принадлежат конкретному процессу и не являются автоматическим каналом UI ↔ ядро.

## 13. Замена встроенных компонентов

### 13.1. Когда использовать replace

Если нужно добавить кнопку в существующее место, начните с `extend`. Если нужен самостоятельный инструмент — с модуля. `replace` нужен, когда вы действительно предоставляете альтернативную реализацию существующего компонента.

Основные объявленные цели текущего хоста:

| Категория | Цели |
| --- | --- |
| Воркспейсы | `workspace.chat`, `workspace.projects`, `workspace.files`, `workspace.board`, `workspace.paint`, `workspace.startup`, `workspace.graph`, `workspace.pipelines`, `workspace.module`, `workspace.log` |
| Боковые панели | `widget.file_manager`, `widget.sessions`, `widget.tasks`, `widget.subagents`, `widget.personality`, `widget.mcp`, `widget.terminal`, `widget.web_search` |
| Верхняя панель | `topbar.main` |
| Агент | `core.agent` |
| Системный модуль | `module.system.<системное_имя>` |
| Кастомный модуль | `module.custom.<системное_имя>` |

Конкретная цель должна быть зарегистрирована и фактически использоваться хостом в вашей сборке. Список целей не означает, что любой кусок любого скрипта можно заменить по строковому имени.

### 13.2. Контракт UI-замены

Для замены встроенного Qt-компонента недостаточно вернуть произвольный `QWidget`: объект должен быть экземпляром исходного класса или его подкласса и сохранять нужный интерфейс.

Например, замена `widget.tasks` должна сохранять контракт `TasksPanel`, включая инфраструктуру боковой панели. Замена чата должна сохранять используемые приложением поля и сигналы. Удаление внутренних методов, к которым обращается остальной код, может сломать приложение даже при успешном прохождении базовой проверки.

Безопасный первый эксперимент — создать оригинальный компонент через `default_factory()` и изменить ограниченную часть его оформления.

Элемент `components`:

```json
{
  "id": "tasks-style",
  "type": "widget",
  "mode": "replace",
  "target": "widget.tasks",
  "entrypoint": "tasks_style:create"
}
```

Файл `tasks_style.py`, включённый в `files`:

```python
def create(context):
    panel = context.default_factory()
    panel.setToolTip("Панель задач с настройкой из плагина")
    return panel
```

Это минимальный пример механизма замены, а не полный редизайн. Для своего интерфейса изучите исходный класс и создайте совместимый подкласс. Храните его в пакете; не заменяйте `ui/panels/tasks_panel.py` на диске.

Если выбранная замена падает при построении UI, хост пытается создать встроенный вариант. Это не основание полагаться на автоматическое исправление произвольного поведения плагина; другую стороннюю замену runtime посреди работы автоматически не активирует.

### 13.3. Сохранение дочерних точек расширения

Некоторые компоненты предоставляют интерфейсы другим плагинам. Встроенный чат предоставляет `ui.chat.input.actions` и `ui.chat.message.actions`; верхняя панель — `ui.topbar.left` и `ui.topbar.right`; агент — `core.run_events`.

При замене родительского компонента нельзя молча считать, что его дочерние интерфейсы по-прежнему работают. Если сохраняете их, укажите реальные версии в `provides_contracts` и действительно вызывайте соответствующие механизмы в своём коде.

Фрагмент компонента замены чата:

```json
{
  "provides_contracts": {
    "ui.chat.input.actions": "1.0",
    "ui.chat.message.actions": "1.0"
  }
}
```

Это декларация совместимости, а не реализация кнопок. Если заявить контракт и не предоставить его, менеджер не сможет доказать по вашему JSON, что вы написали неверную логику.

Полная замена `core.agent` требует знания интерфейса существующего агента. Для первого плагина используйте модуль или `core.tool.execute`; универсальный пустой объект вместо агента не подходит.

## 14. Зависимости, приоритеты и конфликты

### 14.1. Что делает приоритет

Если два включённых плагина претендуют на одну исключительную замену, выбирается подходящий компонент более высокого плагина. Оба участника могут получить предупреждение. Непересекающиеся компоненты продолжают работать, если их зависимости остаются выполнены.

Приоритет не означает «весь верхний плагин стирает весь нижний». Для независимых добавлений это порядок участия, для замены — выбор реализации, для фильтров — порядок преобразований.

Порядок и переключатели применяются после перезапуска приложения. Менеджер не должен менять цепочку текущего запуска агента из-за перетаскивания плитки.

### 14.2. Что приоритет не решает

- Не объединяет произвольные тела Python-функций.
- Не проверяет смысл всех изменений плагина.
- Не создаёт изолированные окружения для двух несовместимых версий библиотеки внутри одного процесса.
- Не гарантирует совместимость ручного monkey patching или обращения к приватным атрибутам.

По возможности используйте узкие точки расширения и объявляйте зависимости. Прямой доступ к объектам приложения технически возможен, но менеджер не сможет надёжно обнаружить все последствия такого вмешательства.

### 14.3. Python-зависимости

Пример поля всего пакета:

```json
{
  "requires_packages": ["httpx>=0.27,<1"]
}
```

Это фрагмент манифеста, а не готовый пакет. Зависимости проверяются в окружении Toshy. **Автоматическая установка отключена.** Импорт ZIP не запускает `pip`, не создаёт отдельный `venv` и не исполняет установочный скрипт.

Сообщение о недостающем пакете означает, что его нужно установить в окружение, которым действительно запускается Toshy. Команда имеет форму:

```bash
python -m pip install "httpx>=0.27,<1"
```

Здесь `python` — конкретный интерпретатор окружения Toshy. На вашей системе команда может называться `python3` или указывать на `venv`. Не устанавливайте зависимости в случайный системный Python и не заменяйте Qt-библиотеки Toshy без проверки совместимости.

Текущий формат зависимостей поддерживает имена и диапазоны версий, но не URL-зависимости и не extras вида `package[feature]`. Поддерживаются маркеры окружения, если они нужны для платформенных различий.

Если библиотека нужна только одному дополнительному компоненту, объявите `requires_packages` у него. Глобальная зависимость блокирует весь плагин, компонентная — соответствующую часть и её зависимые части.

### 14.4. Зависимость от другого плагина

Фрагмент корня `plugin.json`:

```json
{
  "requires_plugins": {
    "other.shared-tools": ">=1.0,<2"
  }
}
```

Другой плагин должен быть установлен, включён и подходить по версии. Простого наличия его папки недостаточно.

### 14.5. Зависимость от компонента и интерфейса

Фрагмент компонента:

```json
{
  "requires_components": ["author.counter/main"],
  "requires_contracts": {
    "ui.topbar.right": ">=1,<2"
  }
}
```

`requires_components` требует работы конкретной части. `requires_contracts` требует интерфейса определённой версии независимо от того, кто его предоставляет. Такая зависимость не создаёт обмен данными и не переносит объекты между процессами.

`group` объединяет связанные части одного пакета: если одна из них недоступна, менеджер исключает всю связанную группу. Используйте это для частей, которые не имеют смысла по отдельности. Не создавайте циклические зависимости.

Версии пакета, API и контракта — разные величины. Плагин версии `2.3.0` может работать с API `1` и предоставлять собственный интерфейс версии `1.0`.

## 15. Файлы, данные и переносимость

### 15.1. Что включается в ZIP

`files` — явный список разрешённого содержимого. Если вы создали `utils.py`, но не включили его или содержащую его папку в `files`, экспорт его не подхватит.

Например, для относительного импорта из соседнего файла:

```python
from .utils import format_value
```

в пакет должны входить оба исходника. Внутри вложенной папки используйте относительные импорты так же, как в обычном Python-пакете. Toshy загружает entrypoint под собственным именем пакета; `import utils` может найти чужой модуль или завершиться ошибкой.

`plugin.json` включается автоматически. Его нельзя добавлять как элемент `files`. Файл `LICENSE` и картинка должны существовать и входить в состав. Пути к entrypoint и содержимому модулей также проверяются.

### 15.2. Что исключается

При обычном экспорте отфильтровываются, в частности:

- `.git`, `.venv`, `venv`, `env`, `__pycache__`, `node_modules`;
- папки `logs`, `sessions`, `runtime`;
- `.env`, `.env.*`, файлы с именами `auth.json`, `credentials.json`, `secrets.json`, `oauth_tokens.json`;
- `.pyc`, `.pyo`, `.log`, `.pem`, `.key`;
- служебные файлы с префиксом `.toshy-`.

Не кладите нужную пользователю статическую папку под зарезервированное исключаемое имя вроде `runtime`: она не войдёт в пакет. Проверяйте фактический список экспорта.

Фильтр имён не ищет пароли внутри Python-кода, изображений или произвольно названного JSON. Просмотрите включаемые файлы самостоятельно.

Для скопированных MCP-модулей генератор очищает машинные параметры запуска, локальные значения окружения и учётные данные в стандартных серверных описаниях; локальная установка зависимостей не переносится как готовый `venv`. После установки на другом устройстве сервер может требовать настройки и установки заново.

### 15.3. Где хранить пользовательские данные

Установленный код имеет отдельные папки версий. Запись настроек рядом с `plugin.py` связывает данные с конкретной версией и затрудняет обновление.

Для фабрик с контекстом используйте `context.data_dir`. Например, **внутри `create(context)`**, после создания виджета счётчика:

```python
import json

state_file = context.data_dir / "counter.json"
try:
    saved = json.loads(state_file.read_text(encoding="utf-8"))
    value = saved.get("count", 0)
    widget.count = value if isinstance(value, int) and value >= 0 else 0
except (OSError, ValueError, AttributeError):
    widget.count = 0
widget.label.setText(f"Нажатий: {widget.count}")


def save_state():
    state_file.write_text(
        json.dumps({"count": widget.count}, ensure_ascii=False),
        encoding="utf-8",
    )


context.register_cleanup(save_state)
```

Этот фрагмент предполагает `widget = CounterWidget(context.parent)` перед ним и `return widget` после него. Сохранение произойдёт при штатной очистке; при аварийном завершении последнее значение может потеряться. Для важных данных реализуйте периодическое/событийное сохранение и атомарную запись.

`data_dir` общая для версий плагина, поэтому при изменении формата данных продумайте миграцию. Удаление кода через менеджер сохраняет пользовательские данные; оно не равнозначно удалению всех следов плагина.

При `path`-модулях объект `Module()` создаётся без `PluginContext`. Не добавляйте обязательный аргумент `context` в его конструктор, ожидая, что реестр его передаст. Для сложной инициализации используйте существующий жизненный цикл модуля или осознанно реализуйте компонент через `entrypoint`.

### 15.4. Windows и Linux

- Используйте `pathlib.Path`, не собирайте пути строкой с `\\` или `/`.
- В манифесте оставляйте переносимые относительные пути с `/`.
- Избегайте различающихся только регистром файлов: `Widget.py` и `widget.py` конфликтуют на типичных Windows-установках.
- Не используйте имена `CON`, `NUL`, `PRN`, `COM1` и другие зарезервированные Windows-имена, завершающие точки/пробелы и запрещённые символы.
- Не распространяйте символические ссылки и специальные файлы.
- Не предполагайте наличие Bash, `/bin/sh`, `apt`, `dnf` или PowerShell на всех платформах.
- Не зашивайте абсолютные пути своей машины.
- Если поддерживается только одна ОС, честно укажите её в `compatibility.platforms`.

### 15.5. Ограничения формата

| Ограничение | Значение |
| --- | --- |
| Версия формата / API | `1` / `1` |
| Компонентов в пакете | До 128 |
| Элементов `files` | До 256 |
| Файлов/элементов архива | До 4096 |
| Суммарный распакованный размер | До 256 МиБ |
| Размер ZIP при установке | До 256 МиБ |
| Один обычный файл | До 32 МиБ |
| `plugin.json` | До 128 КиБ |
| Картинка плагина | До 2 МиБ |

Не используйте пакет плагина для передачи огромного окружения или весов модели. Скачивание внешних ресурсов при необходимости — отдельная функциональность, которую нужно реализовать и объяснить пользователю.

## 16. Экспорт, установка и выпуск обновления

### 16.1. Проверка состава не равна тесту

«Проверить состав» проверяет манифест, пути, наличие объявленных файлов и ограничения упаковки. Проверка не вызывает `create`, не запускает инструмент, не выполняет сетевое подключение и не гарантирует отсутствие ошибок Python во время работы.

После успешной проверки становится доступен «Экспорт ZIP…». Если включённые исходники изменились между проверкой и экспортом, приложение попросит проверить состав снова. Это нормальная защита от экспорта другого содержимого.

### 16.2. Три разные копии

| Копия | Для чего нужна | Что редактировать |
| --- | --- | --- |
| Исходная папка | Разработка, Git, метаданные | Здесь меняется код |
| Экспортированный ZIP | Передача и установка | Не редактировать вручную; пересобрать из исходников |
| Установленная папка версии | Выполнение выбранной версии | Не использовать как рабочую папку разработки |

Правка исходников без повторной установки не обновляет установленную копию. Простое копирование исходной папки рядом с `plugins/` также не регистрирует пакет в менеджере.

### 16.3. Локальный цикл разработки

1. Измените код в исходной папке.
2. Если этот ID/версия уже устанавливались, увеличьте версию в `plugin.json`.
3. Убедитесь, что новые файлы включены в `files`.
4. Нажмите «Проверить состав» и проверьте список.
5. Экспортируйте ZIP вне исходной папки.
6. Импортируйте его через «Библиотека → Импорт ZIP…».
7. Проверьте переключатель; новый плагин по умолчанию выключен, обновление сохраняет его состояние.
8. Полностью перезапустите приложение.
9. Проверьте функцию и предупреждения.

В текущем механизме нет обещания горячей перезагрузки Python-кода. Перезапуск ядра не заменяет полный перезапуск UI после изменений плагинов.

### 16.4. Структура ZIP

В корне должен находиться `plugin.json`, рядом объявленные файлы. Дополнительная внешняя папка `my-plugin/`, внутри которой лежит весь пакет, не подходит для прямой установки таким архивом.

Используйте штатный экспорт, чтобы получить корректную структуру. GitHub-архив ветки с исходниками и устанавливаемый Toshy-пакет — разные артефакты.

### 16.5. Удаление и восстановление

Чтобы убрать активный плагин, выключите его и полностью перезапустите Toshy, затем используйте «Удалить плагин…». Текущая сессия приложения может ещё держать прежний пакет, поэтому удаление активного кода ограничено.

Если после разработки интерфейс не позволяет открыть менеджер, закройте Toshy и сделайте резервную копию `plugins/state.json`. В текущей структуре хранилища список `enabled` содержит ID включённых плагинов. Удаление проблемного ID из **этого списка** при полностью остановленном приложении отключает его на следующем старте. Сохраните корректный JSON и остальные поля; не удаляйте случайные папки или записи версий вместо диагностики.

Для возврата на известную рабочую версию можно импортировать её сохранённый ZIP. Прямой импорт более старой версии сопровождается предупреждением. Откат кода не откатывает пользовательские данные: миграции данных нужно проектировать отдельно.

## 17. Размещение на GitHub и в каталоге

### 17.1. Прямой импорт публичного релиза

Для распространения без общего каталога:

1. Создайте свой репозиторий с исходниками, `README.md` и лицензией.
2. Экспортируйте рабочий Toshy-пакет.
3. Создайте GitHub Release для этой версии.
4. Прикрепите **готовый ZIP плагина как release asset**.
5. Передайте пользователю ссылку на репозиторий, конкретный релиз или ZIP-файл релиза.

Пользователь открывает «Библиотека → Импорт с GitHub…». Для публичных пакетов подключать аккаунт GitHub к Toshy не требуется. Сеть и доступность GitHub при этом нужны.

Поддерживаемые формы ссылки, где `OWNER` и `REPOSITORY` заменяются реальными значениями:

```text
https://github.com/OWNER/REPOSITORY
https://github.com/OWNER/REPOSITORY/releases/latest
https://github.com/OWNER/REPOSITORY/releases/tag/1.0.0
https://github.com/OWNER/REPOSITORY/releases/download/1.0.0/author.counter.zip
```

Для ссылки только на репозиторий используется обычный latest-релиз. Для конкретной версии дайте ссылку на её тег/файл. При нескольких ZIP приложение предложит выбрать пакет. Не кладите в релиз несколько непонятно названных ZIP, если пользователю трудно их различить.

Если готового ZIP в релизе нет, импорт не собирает Python-проект за автора и не устанавливает автоматически зависимости. Автоматические GitHub-ссылки «Source code (zip)» не заменяют подготовленный пакет.

### 17.2. Общий каталог

Каталог и репозиторий отдельного плагина — разные роли. Каталог содержит `catalog.json` со сведениями о пакетах и ссылками на их релизы. Поле «Репозиторий каталога плагинов» предназначено для такого каталога.

Запись каталога включает, помимо названия, ID, версии, описания, автора, лицензии, совместимости и тегов:

- ссылку на картинку из релиза;
- ссылку `archive.url` на ZIP из релиза;
- размер `archive.size` в байтах;
- SHA-256 ZIP в `archive.sha256`;
- ссылку `source` на соответствующие исходники;
- `source_sha256` — отпечаток объявленного содержимого пакета.

`source_sha256` — не SHA Git-коммита и не обязательно SHA ZIP. Его вычисляет функция `source_digest` штатного упаковщика из списка имён и хешей включённых файлов. Для первого прямого импорта с GitHub готовить каталог не нужно.

Для добавления в общий каталог автор подаёт изменения вручную через Pull Request по правилам его владельца. Экспорт в Toshy не создаёт репозиторий, не публикует релиз и не отправляет заявку за вас. Проверка в каталоге не отменяет того, что пользователь устанавливает сторонний код.

Обновления из списка каталога выполняются по нажатию пользователя. При ошибке скачивания/установки прежняя установленная версия должна оставаться доступной. Не путайте целостность скачанного пакета с гарантией безопасности его поведения.

## 18. Как проверять и отлаживать плагин

### 18.1. Проверка упаковки

- `plugin.json` читается как JSON и проходит «Проверить состав».
- Показаны все нужные файлы, включая новые Python-модули и ресурсы.
- Нет секретов, кэша, пользовательских сессий и логов.
- ZIP импортируется в чистую тестовую копию Toshy.
- Изменённый код выпускается с новой версией.

### 18.2. Проверка UI

- Плагин появляется после полного перезапуска.
- Виджет/воркспейс располагается там, где ожидается.
- Кнопки, сигналы, клавиатура и размер окна работают.
- Повторное создание интерфейсных частей не дублирует глобальные подписки и таймеры.
- Тяжёлые действия не блокируют GUI.
- Выключение плагина и перезапуск возвращают обычное поведение.

UI-slot сообщения вызывается для множества сообщений. Не размещайте в каждой такой фабрике новое глобальное соединение с сервером или подписку на всё приложение без управления временем жизни.

### 18.3. Проверка модуля и нод

- Модуль доступен в нужной категории после установки плагина.
- Включён в конфигурации ядра и разрешён проекту.
- Имена инструментов уникальны.
- Вызов с нормальными аргументами возвращает ожидаемый результат.
- Ошибочные аргументы и ошибки внешнего сервиса обрабатываются понятно.
- Ноды видны без запуска ядра, если метаданные доступны статическому анализатору.
- При остановке ядра/отключении модуля освобождаются ресурсы.

### 18.4. Проверка совместимости

- Без сторонних плагинов.
- С обычными расширениями той же UI-области.
- С альтернативной заменой той же цели выше и ниже в списке.
- При отсутствии обязательной зависимости.
- После обновления с предыдущей версии с сохранёнными данными.
- На обеих заявленных ОС либо с честным ограничением платформы.

Проверка конфликта полезна даже если вы единственный автор: намеренно создайте два маленьких компонента `replace` одной цели в тестовой среде и убедитесь, что предупреждение и выбранная реализация соответствуют ожиданиям.

### 18.5. Где искать причину

1. В сообщении «Экспорт» или «Библиотека» после операции.
2. В подсказке жёлтого значка установленного пакета.
3. В различии планируемого состояния и состояния «сейчас» — возможно, нужен перезапуск.
4. В журнале приложения/ядра; ошибки механизма плагинов помечаются `PLUGIN_EVENT`.
5. В консольном traceback, если запускаете Toshy из терминала своего окружения.

Для локального запуска из корня проекта используется `python run_ui.py` с правильным интерпретатором. Не запускайте второй экземпляр над теми же рабочими данными без необходимости; используйте отдельную тестовую копию.

## 19. Частые ошибки

| Симптом | Вероятная причина и действие |
| --- | --- |
| Изменил «Название» в форме, но пакет остался старым | Поле используется при создании; измените `name` в выбранном `plugin.json` |
| Выбрал другую заготовку, а код не изменился | Выбор шаблона ничего не перезаписывает; нужна кнопка создания или добавления компонента |
| «Без шаблона» не проходит проверку | Пустой `components`; добавьте реальную часть |
| «Экспорт ZIP…» неактивен | Выберите правильную папку и выполните успешную проверку состава |
| Просит проверить состав снова | Включённые исходники изменились после проверки |
| `A root plugin.json manifest is required` | ZIP имеет лишнюю внешнюю папку или вообще не является Toshy-пакетом |
| `Entrypoint source is missing` | Неверный `entrypoint` либо исходник не включён в `files` |
| Файл присутствует в исходниках, но отсутствует в ZIP | Не объявлен в `files` или попал под исключение |
| Ошибка существующей версии с другими байтами | Увеличьте `version` и экспортируйте заново |
| Установил ZIP, но ничего не появилось | Новый пакет выключен; включите и полностью перезапустите приложение |
| Перезапустил ядро, а UI старый | Нужен полный перезапуск Toshy |
| `No module named ...` для своего файла | Проверьте `files` и относительный импорт внутри пакета |
| Не установлена Python-зависимость | Установите её в окружение Toshy; импорт пакета не вызывает `pip` |
| Плагин работает частично | Посмотрите предупреждения отдельных компонентов и их зависимости |
| Виджет работает, а инструмент не доступен модели | Проверьте модуль, настройки проекта и `model_visible` |
| Нода не видна при выключенном ядре | Проверьте литеральные метаданные в `__init__.py`, `Module.get_tools()` и полный перезапуск |
| Нода видна, но падает при запуске | Статический анализ не проверяет реализацию; проверьте модуль, аргументы и traceback |
| Две версии одной библиотеки не уживаются | Приоритет плагинов не изолирует Python-зависимости |
| Замена заблокирована | Неизвестная цель, потерянный контракт, зависимость, приоритет или неправильный класс результата |
| «Добавить компонент…» недоступно у установленной версии | Выбрана управляемая папка с `.toshy-receipt.json`; используйте исходный проект |
| Нет пакета при импорте с GitHub | Нужен готовый ZIP в опубликованном релизе, а не только исходники |
| Windows отклоняет пакет, работающий на Linux | Проверьте регистр, зарезервированные имена, символы и переносимые пути |

### Фактическое хранение

В проверенной структуре корень хранилища — `plugins/` внутри корня приложения:

| Путь | Роль |
| --- | --- |
| `plugins/packages/<plugin-id>/<version>/` | Установленный код версии |
| `plugins/data/<plugin-id>/` | Отдельные пользовательские данные плагина |
| `plugins/state.json` | Выбранные версии, порядок и включение |
| `plugins/cache/` | Кэш библиотеки |
| `plugins/runtime/` | Снимки конфигурации текущего запуска |

Это описание для ориентации и восстановления, а не предложение вручную обслуживать менеджер. Обычная установка и обновление выполняются через интерфейс.

## 21. Памятка перед публикацией

1. У пакета уникальный стабильный ID и новая версия для изменённого выпуска.
2. Название и описание объясняют пользователю, что он получит.
3. Выбранный шаблон уже доработан: вместо заглушки есть нужная функциональность.
4. Все компоненты перечислены в `plugin.json`; вспомогательные файлы включены в `files`.
5. Имена модулей и инструментов имеют собственный префикс.
6. Заявленные зависимости и ОС соответствуют действительности.
7. Код приложения не перезаписывается, рабочие данные отделены от установленной версии.
8. Подписки, процессы и другие ресурсы имеют корректное завершение.
9. Для замен сохранены необходимые классы, интерфейсы и реальные дочерние точки расширения.
10. Указана лицензия и сохранены необходимые лицензии включённого стороннего кода. Шаблон создаёт MIT для новой заготовки; при копировании готового модуля с `LICENSE` переносит его лицензию. Проверьте, что итоговые `LICENSE` и `license` описывают реальный состав пакета.
11. Проверены файлы на секреты и локальные абсолютные пути.
12. Выполнены импорт, включение, полный перезапуск, функциональная проверка, отключение и обновление в тестовой копии Toshy.
13. Для GitHub прикреплён именно устанавливаемый ZIP к релизу, а README объясняет настройку и ограничения.

### Если запомнить один рабочий маршрут

**Создать исходники → написать код → проверить `plugin.json` и состав → экспортировать ZIP → импортировать через библиотеку → включить → полностью перезапустить → проверить функцию.**

Для следующего выпуска: изменить исходники, повысить версию и повторить этот маршрут начиная с проверки состава. Составной плагин проходит тот же путь: количество компонентов не меняет способ установки.


### Release installation and compatibility (Toshy 0.1.0, API 1)

Managed installations keep immutable code under a version directory and mutable
application data under a separate root. `APP_PATHS.code_root` identifies application
code; `APP_PATHS.root` identifies its data in a managed installation. Plugin code
stays in `context.plugin_dir`; write settings, databases and downloaded dependencies
to `context.data_dir`. Never modify an installed application or plugin package.

For Qt organization/application settings use `from ui.settings import QSettings`,
or an explicit INI filename under `context.data_dir`. Direct native QSettings on
Windows can write to the registry outside the installation's data directory.

`compatibility.toshy` is checked against the real application version.
`compatibility.architectures` may declare `["x86_64"]` or `["aarch64"]`; omit it
only for genuinely architecture-independent code. The first supported Toshy
release targets Windows/Linux x86-64. Declare native dependencies accordingly.

The optional manifest integer `data_schema` defaults to 1. Keep the same schema
only while existing data remains compatible. Automatic plugin updates reject a
schema change until an explicit migration is supplied; they do not run arbitrary
migration code while the old UI/core may still be using the data.

Catalog upgrades validate the package, version, platform, host constraints and
dependencies before changing the selected version. Existing active processes keep
their frozen versions until a complete restart. Old package versions are retained
for rollback; data is not reset or automatically downgraded.
